X/Twitter Keyword & Hashtag Tweet Search

Search X (Twitter) by keyword, phrase or hashtag and get tweet text, author, engagement metrics, media and language. Every row says which keyword found it. No login required.

Published README

Read the full published documentation

X/Twitter Keyword & Hashtag Tweet Search

Give this actor a list of keywords, phrases or hashtags and it pulls back matching X (formerly Twitter) posts — full text, engagement counts, media and the author who wrote each one. No sign-in, cookies or developer credentials needed; it reads the same public search results any visitor sees.

What this actor does

  • Runs each entry in keywords as its own independent search, so a single job can cover several unrelated topics at once.
  • Targets up to 1,000 posts per keyword via maxTweets; how many actually come back depends on how much volume that keyword has on X. A 300-row target has been verified (about 297 s); 500/1,000 are not verified, so treat maxTweets as a target, not a promise.
  • Runs several X search lanes (latest, media, opt-in media-product, links, optionally replies) and walks backwards through since_time/until_time windows. Guest search has no cursor paging; time-window backfill is the only way past the ~20-row page cap (a product=Media page can return 41-45 rows).
  • Latest returns newest-first. Top is engagement-ranked output, not X's real Top timeline: X never serves Top to logged-out callers, so the actor collects Latest pages and sorts them by like count client-side.
  • Narrows by language, date window, retweets/replies, verification, media presence, quotes, mentions, author, reply target, conversation id, and minimum like/retweet/reply counts.
  • Supports multi-word matchMode (all, any, exact) and excludeWords.
  • With onlyNew enabled, returns only posts newer than the previous run for the same monitorId + keyword. The actor persists a numeric snowflake watermark and an overlap window in the key-value store.
  • Stamps every row with searchTerm, source (x-search or bing-news), sourceLane (latest / media / media-product / links / replies / window / bing / bing-title-only) and degraded.
  • Emits a typed status row for a keyword that needs attention and one summary row per run.
  • Empty fields are omitted: never null, empty strings or empty arrays/objects in the output.

Output per post

Core fields on every post record: id, url, text, createdAt, language (when X reports one), searchTerm, source, sourceLane, degraded, type: "post" and collectedAt.

Engagement comes through replyCount, retweetCount, likeCount, quoteCount, bookmarkCount, and viewCount, plus a computed engagementRate — (likes + retweets + replies + quotes) ÷ followers — included only once the author's follower count is known and nonzero. Missing retweets/quotes/bookmarks/views/followers/bio are backfilled from the FxTwitter mirror after the X refresh; X values always win and only missing fields are copied.

Post-type context: isReply, isRetweet, isQuote, isNoteTweet, and, for replies, conversationId, inReplyToTweetId, inReplyToUserId, inReplyToUsername, parentTweet (a nested summary of the post being replied to, when available). Every post row also carries recordType: "post", sourceUrl (the canonical post URL) and scrapedAt.

Entities parsed out of the text: hashtags, mentions, urls, cashtags.

Attachments and extras, when present: media (one entry per photo/video/GIF with type, url, previewImageUrl, width, height, durationSeconds, viewCount, altText, mediaKey, canMediaTag, focusRects, variants with url/contentType/bitrate), quotedTweet / quotedTweetId, poll, card, possiblySensitive, withheldInCountries, place, postedFrom, isEdited, editControl (edit history metadata), newsActionType.

The author rides along as a nested author object: id, username, name, bio, bioLinks, location, website, followers, following, likesGiven, postCount, mediaCount, createdAt, profileImageUrl, bannerUrl, profileImageShape, isBlueVerified, verified, verifiedType, isProtected, professionalType, superFollowEligible, superFollowedBy, superFollowing, hasGraduatedAccess, translatorType and pinnedTweetIds. Fields X does not expose for a post are omitted.

Output per status row

When a keyword needs attention, the actor pushes one typed record:

{
  "type": "status",
  "status": "blocked",
  "message": "X guest search refused this network right now...",
  "searchTerm": "apify",
  "collectedAt": "2026-06-02T10:03:41+00:00",
  "source": "none",
  "sourcesTried": ["x-search", "bing-news"],
  "xAttempts": 96,
  "xOk": 0,
  "xLastStatus": 404,
  "bingDiscovered": 0,
  "bingHydrated": 0,
  "bingTitleOnly": 0,
  "bingRows": 0,
  "targetRows": 20,
  "uniqueRows": 0,
  "budgetSeconds": 105,
  "budgetExhausted": false,
  "degraded": true,
  "partial": false
}

Statuses:

Status Meaning
noInput No keywords were provided.
noResults A source answered and returned zero matching posts (or every collected row was already seen by onlyNew).
blocked No source answered: X refused and Bing was unavailable or skipped because the query uses operators.
partial Rows were returned but the target was not reached (budget/limits stopped the walk, a full page appeared at the oldest edge, or X was blocked and Bing supplied fewer rows than requested). Reaching the target exactly is ok, even when rows are degraded.
budgetExhausted The per-keyword budget ran out before any source answered.
enrichmentPartial Rows were returned, but one or more per-tweet enrichment lookups failed.

xOk counts only X bursts that returned a parseable page of posts. An HTTP 200 with an empty payload or an empty timeline is treated as a refusal/no-answer, so it cannot mask blocked or budgetExhausted.

Every run also ends with one type: "summary" row carrying recordType: "runSummary", scrapedAt, startedAt, finishedAt, keywords, postRows, statusRows, bySource, sourcesTried, aggregate xAttempts / xOk / bingDiscovered / bingHydrated / bingTitleOnly, degradedKeywords, partialKeywords, blockedKeywords, durationSeconds, monitorId and onlyNew. Consumers that count type: "post" are never confused by status or summary rows.

Known hard limits

Measured directly (no proxy, no cookies, no browser) in live probes on 2026-11-08:

  • Guest search is a lottery. Only ~6% of Latest bursts answered in a 32-attempt probe, and the 300-row backfill used 5,259 attempts / 20 answered bursts (0.38%). The same query can return 20 rows in seconds later, but there is no SLA.
  • No real Top. X serves Top only to signed-in callers, so Top output is a client-side like-sort of the Latest rows that were collected.
  • No cursor paging. One answered page is ~20 rows; product=Media can return 41-45. Backfill beyond one page is time-window walking only.
  • 300 rows is the measured backfill ceiling. 300/300 was reached on bitcoin; 500 and 1,000 are unverified targets.
  • Bing News is stale and shallow. It discovers newsworthy posts only (0/65 sampled rows were <24 h old, 53/65 were <7 d) and walks at most 5 RSS pages (~50 unique ids). It cannot honour operator queries.
  • Monitoring is duplicate suppression, not complete coverage. onlyNew plus the overlap window protects the page boundary; posts published between runs can be missed when a keyword produces more than one page per interval.
  • Enrichment depends on one third-party mirror. FxTwitter fills retweets/quotes/bookmarks/views/author fields; vxtwitter/fxwitter/fixupx were unusable in the same environment. If FxTwitter fails, those fields stay absent; rows are still returned.

Use cases

  • Brand monitoring — schedule the actor with onlyNew to catch new mentions without repeating old rows.
  • Trend and topic tracking — measure how a subject's volume and engagement shift over weeks or months.
  • Breaking-news watch — pair Latest with a tight date range or sinceTime/untilTime to follow a fast-moving story.
  • Content research — surface the highest-engagement posts around a theme for inspiration.
  • Academic or policy research — assemble a dataset of public discourse on a topic, language or time period.
  • Competitor comparison — run several competing keywords side by side and compare volume and engagement.

FAQ

Do I need an X account or developer credentials? No — there's no credential field in the input at all. The actor reads what any logged-out visitor can already see on X's own search.

How many posts will I actually get per keyword? Up to maxTweets, but that's a ceiling, not a promise. Guest search answers intermittently and returns ~20 rows per answered page (41-45 on an answered product=Media page). The actor multiplies those pages with lanes and time windows. A 300-row target has been verified; targets above 300 are unverified. An obscure keyword may return only a handful.

Why did I get a different count on a second identical run? X's logged-out search doesn't expose stable, full pagination, and what it surfaces can shift between requests. If you need more rows, use onlyNew: false, narrow the date window, or add lanes rather than assuming something broke.

Should I use Top or Latest? Latest for anything time-sensitive — breaking news, live mentions, a campaign in progress. Top gives you the strongest engagement among the rows the actor could collect, but it is a client-side like-sort of Latest results, not X's real Top timeline (X does not serve Top to guests).

How does only-new monitoring work without a cursor? The actor saves lastMaxId (numeric 19-digit snowflake), lastRunAt and the last 1,000 seen ids in the key-value store under xkw:<sha1(monitorId + keyword)>. Each run searches from lastRunAt - overlapMinutes (capped by maxAgeDays) and keeps rows with an id numerically above the watermark or created inside the overlap window and not already seen. A blocked run never advances the watermark. Bing-only fallback rows are remembered as seen so they are not re-emitted, but they leave the X gap open for the next run.

Is a proxy required? No, it's optional. Add one mainly if you're running large or frequent jobs from the same IP and want extra headroom against rate limiting.

How current is the data? Fully live — each run queries X at the moment it executes. Put the actor on a schedule with onlyNew for ongoing monitoring. Bing News fallback rows are not real-time: in live probes only 1.2% were under 24 hours old.

Why is a row marked degraded: true? It came from the Bing News fallback (hydrated or title-only). Those rows are newsworthy-only, can be days or years old, and lack retweets/quotes/views/bookmarks/followers until the enrichment layer fills what it can.

How do I get the results into another tool? Pull the dataset from the run page or the Apify API, wire up a webhook, or connect it to Zapier, Make, Google Sheets, or similar no-code tools.

Is this affiliated with X? No. This is an independent, third-party actor that reads publicly available X search results.
